# Dewey 0.5.0 first-integration implementation plan

**Status:** frozen for implementation  
**Baseline:** `origin/main` at `847b6c428dfea01240b1d8f93adbed30d86fc191`  
**Target:** an installable, reviewed 0.5.0 release candidate; no merge, tag, or publication

This public plan addresses the eight issues confirmed by Dewey's first installed-wheel
Django/Huey integration. It is intentionally independent of private planning context.

## Frozen outcomes

1. **Importable dispatch.** `DEWEY["DISPATCH"]` names a module-level callable resolvable
   by Django's `import_string`. Object traversal such as
   `myapp.tasks.adapter.dispatch` is unsupported. A module-level wrapper remains supported;
   the preferred path is `dewey.contrib.django_huey.dispatch`.
2. **Explicit database roles.** Producer creation coupled to business data uses the same
   Django alias and transaction as that business write. Dispatcher and worker aliases are
   independent post-commit connections. Two aliases pointing at one physical database are
   still two connections and two transactions; docs must never imply otherwise.
3. **Safe Django/Huey workers.** First-class wiring uses `huey.contrib.djhuey.HUEY`,
   registers Dewey processing once with Huey retries disabled, and applies
   `huey.contrib.djhuey.close_db` around worker execution.
4. **Retry timing independent of recovery.** Due `FAILED` rows are directly and atomically
   claimable. Dispatchers pace their next wait to the earliest due retry or scheduled task,
   bounded by normal LISTEN/poll/stop behaviour. Sweeps remain crash recovery.
5. **First-class contrib module.** `dewey.contrib.django_huey` exports module-level
   `adapter` and `dispatch`, validates configuration with actionable
   `ImproperlyConfigured` errors, and supports `DEWEY["WORKER_DATABASE"]` separately from
   dispatcher `DEWEY["DATABASE"]`. Core Dewey remains importable without Django or Huey.
6. **Deadline and expiry.** A nullable timezone-aware absolute `expires_at`, terminal
   `EXPIRED`, and an expiry audit timestamp span framework-free types, SQLAlchemy sync and
   async, Django, migration, queries, stats, and docs. Expiry is enforced atomically before
   dispatch and again before handler invocation; `now == expires_at` is expired and consumes
   no handler attempt.
7. **Race-safe idempotent creation.** `create_or_get_task()` exists for Django and
   SQLAlchemy sync, with async parity, requires a non-empty idempotency key, returns the
   task, and raises `IdempotencyConflictError` naming only differing fields when immutable
   creation inputs conflict. It uses a savepoint/nested transaction so a race loser does not
   abort its caller's transaction.
8. **Checks, doctor, and readiness.** Lightweight Django system checks validate static
   configuration. `manage.py dewey_doctor` provides human and stable JSON findings with
   meaningful exit status. Database-backed dispatcher heartbeats support all backends,
   multiple dispatchers, queue/alias matching, bounded updates and cleanup, and fail-closed
   readiness without making heartbeat failure corrupt dispatch.

## Bounded design decisions

- Direct retry eligibility is implemented by claim queries accepting due `FAILED` rows;
  no pre-claim sweep is required.
- Idempotency compares post-serialization/default-resolution values for task type, args,
  kwargs, queue, priority, max attempts, original scheduled time, expiry, and every other
  persisted immutable creation-contract field. Metadata does not participate because it is
  operational context rather than execution definition.
- Existing `scheduled_for` is reused for retry availability and therefore mutates. Dewey
  persists an internal immutable creation-time schedule snapshot so an identical request can
  still match an existing task after retries or completion. This is an implementation field,
  not a second scheduling API.
- Expiry records a dedicated audit timestamp; status `EXPIRED` is the reason. Expired rows
  remain queryable and cannot be manually retried.
- Heartbeats store only a random instance identifier, Dewey version, backend kind,
  non-secret database alias/identifier, queues, and start/last-seen timestamps. They do not
  store DSNs, credentials, hostnames, process environment, or host secrets.

## Dependency-ordered implementation

### P0 — baseline and plan

- Fetch and branch from current `origin/main`, not a stale release branch.
- Record exact base/tag reality, run fast gates, and reproduce the broken dispatch path.
- Land this plan and keep a file/contract dependency map.

### P1 — integration correctness and contrib wiring

Correct import examples/errors and producer/dispatcher/worker alias guidance. Add
`dewey.contrib.django_huey`, `WORKER_DATABASE`, one-time registration, `close_db`, optional
import boundaries, and focused Django/Huey/Postgres tests.

### P2 — schema and state foundations

Add `EXPIRED`, `expires_at`, expiry audit timestamp, immutable original schedule snapshot,
heartbeat schema/contracts, Django `0002`, SQLAlchemy metadata/indexes, public exports,
queries, and stats. Prove fresh and 0.4-to-0.5 migrations before behavioural work.

### P3 — retry scheduling and expiry enforcement

Extend sync, async, and Django claims for due retries; add earliest-due pacing; enforce
expiry at claim and process gates; preserve ordering, multi-dispatcher safety, batch limits,
release-on-transport-failure, database-outage survival, and LISTEN/poll correctness.

### P4 — idempotent creation

Implement typed conflicts and transaction-preserving create/get across Django, SQLAlchemy
sync, and SQLAlchemy async. Cover serializer normalization, lifecycle-independent matches,
all immutable-field conflicts, and real concurrent creators.

### P5 — checks, doctor, and heartbeat integration

Emit bounded heartbeats from all dispatchers, add freshness/query/cleanup helpers, register
Django checks, and add doctor human/JSON output. Test healthy, stale, absent,
wrong-alias/queue, unsafe routing, disabled recovery, incomplete registries, and unavailable
database states.

### P6 — docs, packaging, and installed-wheel proof

Update README, settings/getting-started/adapters/concepts/query/onboarding docs, changelog,
publish plan, version exports, CI, wheel smoke, and the release-candidate report. Every
example must execute in its documented shape.

### P7 — integrated critical review

Review the exact integrated head for transaction atomicity, concurrency, state safety,
migrations, optional imports, dispatcher outage behaviour, and documentation truth. Repair
verified findings once, run targeted regressions, then perform one focused verification.

### P8 — exact-head release gates and handoff

Commit the final candidate, run every mandatory gate on that SHA, push/open a PR if normal
authentication works, and produce the operator checklist. Stop before merge/tag/publish.

Shared hotspots—states/types, both ORM models, dispatcher protocols, claim queries, and all
three executors—are integrated sequentially. Builders must not edit the same hotspot in
parallel.

## Acceptance evidence

The release candidate must demonstrate:

- module-level dispatch import and Django/Huey `close_db` wiring from an installed wheel;
- same-alias producer rollback and deterministic proof that split aliases are not atomic;
- retry near its policy due time despite a long recovery sweep, including earliest-due wake;
- expiry boundaries, scheduled/retry-after-expiry, broker-delayed delivery, manual actions,
  and concurrent claim/process races on real PostgreSQL;
- identical and conflicting idempotent creation, serializer normalization, surrounding
  transaction preservation, and real concurrent creators on all ORM paths;
- fresh/stale/absent/wrong-alias/wrong-queue heartbeat and doctor JSON findings;
- optional core imports without Django/Huey and actionable contrib failures;
- fresh migration, 0.4.0 upgrade, rollback/reapply, drift check, and real index/constraint
  inspection.

Mandatory exact-head commands/evidence include `make lint`, `make format-check`,
`make typecheck`, `make test`, `make test-integration`, supported Django/Huey lanes,
`uv build`, `twine check dist/*`, wheel contents audit, extended `make wheel-smoke`,
optional-extra import matrix, public/private boundary scan, `git diff --check`, clean
`git status -sb`, and exact SHA capture.

## Compatibility and migration notes

`create_task()` remains compatible, including duplicate-key integrity errors.
`create_or_get_task()` and `WORKER_DATABASE` are additive. Existing rows have no deadline.
Status consumers must accept `expired`. Django receives migration `0002`; SQLAlchemy users
must apply documented additive DDL because `metadata.create_all()` does not alter existing
tables. Custom dispatch backends may require new due-time/heartbeat capabilities and must be
called out explicitly in the changelog.

## Hard stop

After every gate passes on one committed SHA, produce the 0.5.0 release-candidate report and
stop. Do not merge to `main`, create or push `v0.5.0`, publish to TestPyPI/PyPI, modify a
downstream consumer, force-push, use secrets, spend money, or deploy anything.
